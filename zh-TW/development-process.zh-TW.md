# 開發流程

擁有安全程式碼庫最關鍵的因素之一，就是紮實的開發流程：「預防勝於治療」。本文件提供了 [Nascent](https://www.nascent.xyz) 團隊認為行之有效的*範例*開發流程。除了能整體提升程式碼品質之外，本流程也是我們[審計就緒檢查清單](audit-readiness-checklist.zh-TW.md)的搭配文件。如果您依循以下流程進行開發，理應能自然而然地完成該檢查清單中的大部分項目。

> **使用方式**：本文件可作為開發 SOP 照表操作。每個階段都定義了「產出物」與「完成標準（gate）」——**上一階段的完成標準未達成前，不應進入下一階段**。文中步驟編號（1–22）貫穿全流程，方便在 PR 或會議中直接引用（例如「步驟 7 的 fuzz 測試還沒補」）。

```
功能需求 (Feature Request)
 |
 └> 規格制定 (Specification)
     |
     └> 評估 (Evaluation)（時間 + 複雜度 + 風險）
        |
        └> 實作 (Implementation)
           |
           └> 測試 (Testing)
              |
              └> 部署 (Deployment)
                 |
                 └> 監控 (Monitoring)
```

## 階段總覽表

| 階段 | 步驟 | 主要產出物 | 完成標準（gate） |
| --- | --- | --- | --- |
| 規格制定 | – | 規格文件 | 影響變數盤點完成 |
| 評估 | – | 風險評估紀錄 | 時程／複雜度／風險三項皆有結論 |
| 實作 | 1–2 | Draft PR＋初版實作 | 文件化完成（NatSpec、Safety 註解） |
| 測試 | 3–13 | 測試套件＋CI＋通過的 PR review | 所有測試通過、Slither 乾淨、review 簽核 |
| 部署 | 14–20 | 部署腳本＋審計報告＋監控＋IR 計畫 | 審計修正落實、演練完成 |
| 監控 | 21–22 | 監控儀表板 | 上線後觀察期無異常 |

## 規格制定

**目的**：在寫任何程式碼之前，先把「這個功能要做什麼、會被什麼影響」寫清楚。規格是後續評估、實作與測試的共同依據。

**做法**：記錄下會影響此功能的各類變數，逐項回答：

1. **使用者輸入？** — 哪些函式接受外部輸入？每個輸入的合法範圍是什麼？惡意輸入（極大值、零、非預期地址、畸形資料）會發生什麼事？
2. **時間？** — 功能是否依賴 `block.timestamp`／區塊高度／期限？跨區塊的操作順序是否影響結果？礦工／排序者可操縱的空間有多大？
3. **其他協定？** — 是否呼叫外部合約（oracle、AMM、代幣）？對方失效、回傳異常值或被攻擊時，本功能的行為是什麼？
4. **現有狀態？** — 功能讀取／修改哪些既有狀態變數？與哪些現有功能共用狀態？在什麼狀態組合下不應被執行？

**產出物**：一份規格文件（可以是 issue 或設計文件），包含上述四類變數的盤點、功能的預期行為描述，以及「明確不支援」的情境清單。

**完成標準**：另一位工程師只讀規格就能理解要做什麼、邊界在哪。

## 評估

**目的**：在投入實作前，用規格來評估時程、複雜度與風險，避免「邊做邊發現坑」。

特別撥出時間（建議至少一次專門會議）逐項評估：

1. **實際上這需要花多久時間？** 沒有規格的話，大多數估算都會不準確。以規格中的變數盤點為基礎拆解工作項，再估時程；把測試與文件的時間明確算進去（通常不少於實作本身）。
2. **這份規格是否過於複雜？** 複雜度會導致 bug 並使整體程式碼品質變差。主動尋找簡化空間：能不能砍掉某個參數？能不能拆成兩個獨立功能？若複雜度來自罕見的邊緣需求，考慮直接不支援。
3. **此功能相關的風險有哪些？** 請花充分的時間評估此項。考量該功能可能觸及的每一個模組，逐一寫下「這個模組會受到什麼影響」。接著再回頭檢視被排除的模組，*確認*它們確實不會受到影響（例如：是否共用狀態變數？是否可能被重入？權限是否互相影響？）。

您可能已經（或者上線後將會）有數百萬美元的資產暴露在風險之中。因此，您**必須**考量每個功能可能如何將*全部*資產置於風險之中。一步走錯，代價很可能就是數百萬美元。

**產出物**：評估紀錄（時程結論、簡化決策、受影響模組清單與排除證明）。

**完成標準**：三個問題都有書面結論；若風險評估顯示功能會觸及核心資產流，已規劃對應的額外防護（不變量檢查、限額、暫停機制）。

## 實作

1. **起草一份 PR**
   - 內容包含功能需求與規格說明，讓 reviewer 能對照「意圖」與「實作」。
   - 建議直接開 Draft PR，後續所有討論都留在 PR 上，形成紀錄。
2. **撰寫初版實作**
   - 先完成一版初步實作，目標是把邏輯走通，不急著優化。
   - 對於任何作為使用者進入點的函式，遵循[函式需求-效果-互動-協定不變量 (FREI-PI) 模式](https://www.nascent.xyz/idea/youre-writing-require-statements-wrong)：函式開頭檢查需求（requirements）、接著更新狀態（effects）、然後才進行外部互動（interactions，所有代幣/ETH 轉帳都算）、最後驗證協定不變量（protocol invariants）仍然成立。
   - 記錄所有函式預期的行為（public/external 函式使用 [NatSpec](https://docs.soliditylang.org/en/develop/natspec-format.html)），並加入行內文件/註解。
   - 任何 `unchecked` 的使用都應附上如下的「安全性 (safety)」文件說明：
     ```solidity
     // Safety:
     //  1. a + b: a and b are uint64s, and a is casted up to uint128, so a uint128(uint64) + uint64
     //     cannot overflow
     //  2. c * 2: c is casted up to uint256, so a uint256(uint128) * 2 cannot overflow
     uint256 d;
     unchecked {
       uint128 c = uint128(a) + b;
       d = uint256(c) * 2;
     }
     ```
   - **每一行**組合語言 (assembly) 都要有文件說明/註解。

**完成標準**：實作與規格對得上；NatSpec 與 Safety 註解完整；可以開始寫測試。

## 測試

3. **撰寫初步的具體[測試](https://book.getfoundry.sh/forge/tests.html)**
   - 為實作撰寫初版測試。**每一次的儲存寫入（storage write）都應該被檢查，每一個 revert 都應該被檢查**。逐行檢視實作程式碼，找出所有的儲存寫入，為每一個寫入撰寫斷言；為每一個 `require`/`revert` 條件撰寫觸發它的測試。
   - 對於不會改變狀態的函式（純數學運算），好的做法是設立一個繼承該合約的測試合約，用來直接呼叫並驗證相關運算。
   - 使用覆蓋率工具（例如 Foundry 的[覆蓋率工具](https://github.com/foundry-rs/foundry/pull/1576)，指令 `forge coverage`）來檢視您的測試對程式碼的涵蓋程度，找出沒被測到的分支。
4. **清理實作程式碼** — 移除死碼、統一命名、簡化過度複雜的邏輯。
5. **改善測試**，接著根據發現的任何 bug 回到步驟 4。
6. **執行 [slither](https://github.com/crytic/slither)**
   - 執行 `slither .`，逐項分析輸出結果：真問題就修（回到步驟 4），誤報則記錄理由。
7. **撰寫[模糊測試 (fuzz tests)](https://book.getfoundry.sh/forge/fuzz-testing.html)**
   - 既然您現在對自己的實作相當有信心，就丟隻猴子進去試試看吧。好的模糊測試應該考量所有合法的輸入，並盡可能納入多種狀態轉換的斷言（例如：這個函式是否應該單調遞增/遞減、是否應該始終小於某個值等等）。
   - 實務提示：不要用過度限縮的 `bound`/`assume` 把有趣的輸入排除掉；斷言寫「性質」而不是重算一次實作邏輯。
8. 若發現任何 bug，回到步驟 4。
9. **撰寫整合測試**
   - 您的功能現在很可能確實如您所預期地運作。但在複雜系統中，這樣還不夠。理想情況下，您也應該測試過它對整個系統造成的影響。使用 [Foundry](https://github.com/foundry-rs/foundry) 和 [Echidna](https://github.com/crytic/echidna) 進行有狀態測試，可以讓您測試系統層級的不變量。
   - 若功能與外部協定互動，使用 mainnet fork 測試對真實合約的行為。
10. 若發現任何 bug，回到步驟 4。
11. **整理文件** — 確認 NatSpec 與註解反映最終實作（測試迭代中行為常有變動）。
12. **設置 CI**
    - 透過 Github Actions 進行持續整合 (Continuous Integration)，能在基本事項上協助審查者：至少要跑建置、全部測試與 Slither。
    - [Foundry CI](https://github.com/foundry-rs/foundry-toolchain) 與 [Slither CI](https://github.com/foundry-rs/forge-template/blob/36f0bf7cbc953f071027a1c1783e7e5c7d9613ed/.github/workflows/lint.yml) 都很有幫助。如果您使用 [forge-template](https://github.com/foundry-rs/forge-template)，這兩者可以直接開箱即用。
13. **PR 審查**
    - 實作者只是第一道防線。如果您是審查者，請逐項確認實作者遵循了上述原則：
      - [ ] 每個狀態轉換都有測試（步驟 3）
      - [ ] 每個 revert 都有測試（步驟 3）
      - [ ] 有模糊測試（步驟 7）
      - [ ] 有整合測試（步驟 9）
    - 審查文件，確保實作內容與文件所描述的行為相符。若不相符，請與實作者確認應該更新哪一方。
    - 確保 CI 通過。
    - 檢查常見的疏失（[重入攻擊 (reentrancy)、檢查-效果-互動模式 (checks-effects-interactions pattern) 等](https://docs.soliditylang.org/en/latest/security-considerations.html#pitfalls)）。

**完成標準**：CI 全綠；覆蓋率經檢視無重大缺口；Slither 無未處理項目；至少一位 reviewer 依上述清單簽核。

## 部署

14. **撰寫部署腳本**
    - 部署必須用腳本執行，不要手動逐筆操作。Foundry 提供了[腳本撰寫指南](https://book.getfoundry.sh/tutorials/solidity-scripting)，可用來在本地分支 (local forks) 上測試您的部署流程。
15. **撰寫部署測試**
    - 撰寫測試*每一個狀態轉換*的測試，確保部署完全按照計畫進行，且不會發生任何非預期的變化。其中一種做法是使用 `record` cheatcode。若是要對現有協定進行升級，可以先列出整個協定的所有地址清單，呼叫 record，接著執行升級。然後，對協定中的每個地址呼叫 `accesses`，確認沒有任何 slot 或地址發生非預期的變動。
16. **進行審計**
    - 考量此功能/合約是否需要審計。永遠寧可謹慎，也不要事後後悔。
    - 讓複雜度與程式碼規模來決定是否需要審計、以及該由誰來審計您的合約。
    - 在 Nascent，我們內部有一份審計人員品質的分級清單。建議您向其他開發者請教，了解哪些審計人員值得信賴、哪些則否。有些審計人員只是為了走個過場，也有些是真心在乎能否找出漏洞。
    - 送審前先完成[審計就緒檢查清單](audit-readiness-checklist.zh-TW.md)。
17. **落實審計修正**
    - 每項審計發現都要有處置：修補（附 commit，並比照一般功能走測試流程）或書面記錄接受風險的理由。修補後請審計方複核。
18. **建立監控服務**
    - 建立內部工具，監控系統中的重要面向（關鍵不變量、大額資金流出、權限操作、oracle 異常）。
    - 可使用像是 [Check the Chain](https://github.com/checkthechain/checkthechain) 搭配 [Grafana](https://grafana.com/) 之類的工具，或是使用現成的監控工具，例如 [Tenderly](https://tenderly.co/alerting) 或 OpenZeppelin 的 [Defender Sentinels](https://www.openzeppelin.com/defender)。
    - 具體的警示情境建議參考[上線前資安檢查清單](pre-launch-security-checklist.zh-TW.md)的 PL-9。
19. **準備/更新您的[事件應變計畫](incident-response-plan-template.zh-TW.md)**
    - 新功能可能改變防禦動作（新的可暫停合約、新的權限），對應更新應變計畫與緊急腳本。
20. **部署合約**
    - 依部署腳本執行，部署後立即：驗證合約原始碼、比對鏈上狀態與部署測試的預期、更新地址文件。
    - 完整的上線前把關請走一遍[上線前資安檢查清單](pre-launch-security-checklist.zh-TW.md)。
    - 恭喜，您在安全開發與部署方面，大概已經超越了 99% 的 Solidity 開發者。

**完成標準**：審計修正全數落實、監控與應變計畫就緒、上線前檢查清單完成，才執行主網部署。

## 監控

21. **密切監控接下來幾個小時**
    - 使用您所建立的監控服務，仔細觀察是否有非預期的行為發生，並隨時準備採取行動。
    - 建議做法：部署後前幾小時安排專人盯監控儀表板；確認緊急應變腳本與簽署者處於待命狀態；若協定支援，考慮以較低的資金上限「軟啟動」，穩定後再放開。
22. **放鬆一下，喝杯啤酒吧，這是您應得的。**
