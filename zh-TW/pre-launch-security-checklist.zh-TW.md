# 上線前資安檢查清單

> **使用方式**：本清單供專案團隊或外部廠商在合約部署到主網（mainnet）前逐項檢查。每個項目都有唯一編號（PL-x），包含「檢查項目、重要性說明、執行步驟、通過標準」。執行時請逐項完成並勾選，無法通過或不適用的項目，請在備註欄說明原因並由專案負責人簽核。**所有項目完成前，不應部署主網。**

## PL-1. 公開資安聯絡窗口

- [ ] **檢查項目**：在 GitHub `README.md` 檔案中，醒目地展示資安聯絡信箱，並確保團隊中確實有人會收到並處理這些郵件。

**重要性說明**：白帽駭客或研究人員發現漏洞時，若找不到回報管道，可能直接公開漏洞、或放棄回報，讓專案錯失在被攻擊前修補的機會。

**執行步驟**：
1. 建立專用信箱（例如 `security@yourproject.xyz`），避免使用個人信箱。
2. 將信箱設定為轉發給至少 **2 位**團隊成員（避免單點失效：某人離職或休假時漏信）。
3. 在 GitHub `README.md` 的醒目位置（建議在開頭或獨立的「Security」章節）寫明此信箱。
4. 建議同時在 repo 根目錄加入 `SECURITY.md`（GitHub 會自動在「Security」頁籤顯示），說明回報流程與預期回覆時間。
5. **實測**：從外部信箱寄一封測試信，確認負責成員在 24 小時內確實收到。

**通過標準**：
- `README.md`（或 `SECURITY.md`）中可找到資安聯絡信箱。
- 測試信已寄出且至少 2 位成員確認收到。

## PL-2. GitHub 列出合約部署地址

- [ ] **檢查項目**：GitHub 儲存庫中列出所有合約的正式部署地址（含所在鏈別）。

**重要性說明**：使用者與資安研究人員需要能驗證「鏈上的合約」確實對應「這份原始碼」。缺少官方地址清單時，容易被釣魚合約冒充，發生事件時也難以快速確認受影響範圍。

**執行步驟**：
1. 在 `README.md` 或獨立文件（例如 `deployments.md`）中建立部署地址表格，欄位至少包含：合約名稱、鏈別（Ethereum mainnet、Arbitrum 等）、地址、部署版本／commit hash。
2. 部署完成後立刻更新此表，並將「更新部署地址文件」納入部署 SOP 的固定步驟。
3. 若有 proxy 架構，proxy 與 implementation 地址都要列出。

**通過標準**：
- 每一個已部署（或即將部署）的合約都能在 repo 中查到官方地址。
- 地址經第二人比對鏈上實際部署結果無誤。

## PL-3. 前端介面連結到 GitHub

- [ ] **檢查項目**：專案的前端介面（UI）有明顯的連結指向官方 GitHub 儲存庫。

**重要性說明**：這是使用者從「產品」回溯到「原始碼」的信任鏈。研究人員通常從 UI 進入專案，缺少連結會提高他們檢視程式碼的門檻。

**執行步驟**：
1. 在網站的頁尾（footer）或「關於」頁面加入 GitHub 連結。
2. 確認連結指向正確的官方 organization／repo（而非個人 fork）。

**通過標準**：從正式環境的 UI 上可以在 2 次點擊內到達官方 GitHub repo。

## PL-4. 部署程式碼包含審計修補

- [ ] **檢查項目**：實際部署（或即將部署）的程式碼，已包含資安審計報告中所有建議的修補內容。

**重要性說明**：「審計過」不等於「部署的是審計後修好的版本」。實務上曾發生團隊部署了修補前的舊版本——即使審計已完成，這個落差仍可能讓已知漏洞上線。

**執行步驟**：
1. 列出審計報告中所有的發現（findings）與對應的修補 commit。
2. 確認部署所用的 commit hash **晚於或包含**所有修補 commit（可用 `git merge-base --is-ancestor <修補commit> <部署commit>` 逐一確認）。
3. 部署後，比對鏈上已驗證的原始碼與該 commit 是否一致（見 PL-7）。
4. 由**非**執行部署的第二人複核上述比對結果。

**通過標準**：
- 每一項審計發現都能對應到「已修補的 commit」或「已記錄並簽核的不修補理由」。
- 鏈上部署版本經比對確認包含所有修補。

## PL-5. 完成審計報告回應並發布最終版

- [ ] **檢查項目**：已回應審計初稿報告中所有建議的變更，且審計方已發布包含團隊回應的最終版報告。

**重要性說明**：只有初稿而沒有最終版報告，外界無法確認「團隊實際上處理了哪些問題」。最終版報告是對使用者與整合方的公開承諾。

**執行步驟**：
1. 針對初稿中的每一項發現，逐項回覆處理方式：已修補（附 commit）／確認風險並接受（附理由）／不適用（附理由）。
2. 將回覆送交審計方複核，請審計方確認修補有效。
3. 請審計方發布包含團隊回應（acknowledgement）的最終版報告。
4. 將最終版報告連結放入 repo（例如 `audits/` 目錄或 README）。

**通過標準**：最終版審計報告已公開發布，其中每項發現都有團隊回應與審計方的確認。

## PL-6. 評估是否需要第二次審計

- [ ] **檢查項目**：若審計期間收到大量程式碼修改建議，已認真評估（並記錄評估結果）是否在完成修改後進行第二次審計，最好由另一家審計方執行。

**重要性說明**：問題清單冗長的審計，往往代表審計人員若有更多時間會發現更多問題；而大量修改本身也可能引入新的漏洞。

**執行步驟**：
1. 統計審計發現數量與嚴重程度（Critical／High／Medium／Low）。
2. 參考判斷基準（符合任一項即強烈建議二次審計）：
   - 有任何 Critical 或 High 等級發現，且修補涉及核心邏輯變動；
   - 發現總數偏多（例如超過 15–20 項）；
   - 審計後的程式碼變動量佔核心合約相當比例（例如 diff 超過 10%）。
3. 決策（做或不做、找哪一家）需書面記錄並由專案負責人簽核。

**通過標準**：有一份書面評估紀錄；若評估結果為「需要」，第二次審計已排程或完成。

## PL-7. 在區塊鏈瀏覽器驗證合約原始碼

- [ ] **檢查項目**：所有已部署的合約皆已在 Etherscan（或對應鏈的區塊鏈瀏覽器）完成原始碼[驗證](https://etherscan.io/verifyContract)。

**重要性說明**：未驗證的合約對外只是一團 bytecode，使用者與研究人員無法檢視，會嚴重降低信任，也讓白帽在事件發生時難以協助分析。

**執行步驟**：
1. 使用自動化工具驗證：[Foundry](https://book.getfoundry.sh/forge/deploying.html?highlight=verify#verifying)（`forge verify-contract` 或部署時加 `--verify`）或 [Hardhat](https://hardhat.org/plugins/nomiclabs-hardhat-etherscan.html)（`hardhat verify`）。
2. 多鏈部署時，每一條鏈的瀏覽器都要各自驗證。
3. 逐一開啟每個合約的瀏覽器頁面，確認顯示綠色勾號、原始碼可讀，且 proxy 合約已正確連結 implementation（Etherscan 的「Is this a proxy?」功能）。

**通過標準**：PL-2 地址清單中的每一個合約，在對應區塊鏈瀏覽器上都顯示「已驗證」且原始碼與部署 commit 一致。

## PL-8. 建立漏洞懸賞計畫

- [ ] **檢查項目**：已建立漏洞懸賞計畫（bug bounty program），賞金額度與範圍已公告。

**重要性說明**：懸賞給白帽一個「回報而不是攻擊（或轉賣漏洞）」的經濟誘因。賞金過低等於變相鼓勵研究人員另尋出路。

**執行步驟**：
1. 選擇平台：[Immunefi](https://immunefi.com/)（Web3 主流）或 [HackerOne](https://www.hackerone.com/) 可協助協調；也可自行公告。
2. 定義範圍（哪些合約、哪些類型的漏洞）與各嚴重等級的賞金。
3. 設定賞金額度：無論你一開始認為「高嚴重程度（High Severity）」的合理賞金是多少，都應該再提高 2–10 倍；上線後，Critical 等級的底線應為**風險資產價值（TVL）的 1%**。
4. 定義回報流程與回覆 SLA（例如 48 小時內首次回應），並與 PL-1 的資安信箱串接。
5. 在 README／SECURITY.md／官網公告懸賞計畫連結。

**通過標準**：懸賞計畫已公開上線，範圍、賞金、回報流程明確，且團隊內部已指定負責分派與回覆的人。

## PL-9. 建立監控與警示機制

- [ ] **檢查項目**：已針對協定的關鍵指標建立自動化監控，異常時會主動通知到值班人員。

**重要性說明**：多數攻擊在幾分鐘到幾小時內完成。沒有即時警示，團隊往往是從 Twitter 上得知自己被駭——那時已經太遲。

**執行步驟**：
1. 列出協定的關鍵不變量與風險訊號，至少考慮以下警示情境：
   - 有新的治理提案被提出時發出警示；
   - 若使用 TWAP：每個區塊檢查 TWAP 並與中心化交易所（CEX）價格來源比對，差異超過 10% 即警示；
   - 合約中超過 20% 的代幣在**單一交易**中被移出時警示；
   - 管理權限相關操作（owner 變更、升級、暫停）發生時警示；
   - 協定的核心不變量（如總資產 ≥ 總負債）被打破時警示。
2. 選擇工具建置：[Check the Chain](https://github.com/checkthechain/checkthechain) 搭配 [Grafana](https://grafana.com/) 自建，或使用現成服務如 [Tenderly](https://tenderly.co/alerting)、OpenZeppelin 的 [Defender Sentinels](https://www.openzeppelin.com/defender)。
3. 將警示接到團隊實際會看的管道（Telegram／Slack／電話），並指定值班與升級（escalation）規則。
4. **實測**：在測試網或 fork 環境觸發一次警示條件，確認通知在預期時間內送達。

**通過標準**：每個關鍵風險情境都有對應警示；至少完成一次端到端的警示演練（觸發 → 通知 → 有人回應）。

## PL-10. 準備緊急應變腳本

- [ ] **檢查項目**：已預先寫好並測試過緊急應變腳本，可在遭受攻擊時快速暫停合約或採取其他防禦性行動。

**重要性說明**：事件發生當下腎上腺素飆升、分秒必爭，臨時寫腳本既慢又容易出錯。防禦動作必須是「按下去就能執行」的狀態。

**執行步驟**：
1. 盤點所有可用的防禦動作：暫停（pause）各合約、調整風險參數、撤銷權限、遷移資金等。
2. 為每個動作撰寫可直接執行的腳本，註明：需要哪些簽署者、目標地址、預期效果。
3. 確認多簽簽署者名單與人數門檻，確保在任何時間（含假日、半夜）都湊得齊足夠簽署人。
4. 在 fork 環境**實際演練**每個腳本，確認執行結果符合預期。
5. 將腳本與操作說明存放在事件應變計畫（PL-11）指定的位置，讓所有相關人知道去哪裡找。

**通過標準**：每個防禦動作都有對應腳本、已在 fork 環境演練成功，且簽署流程確認可在短時間內（建議目標：30 分鐘內）完成。

## PL-11. 建立事件應變計畫

- [ ] **檢查項目**：已建立書面的事件應變計畫，明確定義作戰室成員、溝通管道與防禦行動的啟動方式。

**重要性說明**：萬一遭遇駭客攻擊，你會希望**事先**就知道誰該進作戰室、用哪個平台（Discord、Signal 等）與頻道溝通、如何啟動防禦行動。把這些寫成文件，才能在腎上腺素影響判斷力時仍有所依循。

**執行步驟**：
1. 使用[這份範本](incident-response-plan-template.zh-TW.md)建立計畫，填入所有「待填寫」欄位（負責人、頻道、審計方聯絡資訊等）。
2. 確保每個步驟都有指定的負責人與代理人（backup）。
3. 將文件存放在全團隊都能在緊急時刻取得、但不公開的位置。
4. 上線前與團隊走一遍桌面演練（tabletop exercise）：模擬一個攻擊情境，按計畫逐步走過，記錄卡住的地方並修正計畫。

**通過標準**：計畫中沒有未填寫的欄位；所有被指定的負責人都知道自己的角色；至少完成一次桌面演練。
