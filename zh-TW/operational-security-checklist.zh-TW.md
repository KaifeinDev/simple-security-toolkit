## 金鑰管理

### OS-1. 特權金鑰一律使用硬體錢包

- [ ] **檢查項目**：所有具特權的金鑰（多簽簽署者、admin、部署者）皆存放於硬體錢包，私鑰從未以明文出現在連網裝置上。

**重要性說明**：瀏覽器擴充錢包與明文助記詞是惡意軟體的首要目標。硬體錢包確保私鑰不離開裝置，且每筆交易需要實體按鍵確認。

**執行步驟**：
1. 盤點所有特權地址（對照 SM-1 的角色文件），逐一確認金鑰載體。
2. 任何存於熱錢包／密碼管理器／雲端筆記的特權私鑰，立即轉移至硬體錢包並輪替地址。
3. 助記詞備份只以實體形式保存（見 OS-3），嚴禁拍照、截圖或存入任何雲端服務。

**通過標準**：特權地址清單中每一個金鑰都確認為硬體錢包管理；無明文私鑰存放紀錄。

### OS-2. 多簽門檻與簽署者分散

- [ ] **檢查項目**：資金與管理權限由多簽（或 MPC）控制，門檻設定合理，簽署者分散於不同人員、裝置與地理位置。

**重要性說明**：多簽的保護力取決於簽署者的獨立性——五個簽署者若都在同一間辦公室用同款電腦，實際上仍是單點失效。

**執行步驟**：
1. 檢查每個多簽的門檻設定：建議至少 3/5 或 2/3；門檻不可高到「湊不齊人就無法緊急應變」（對照上線前清單 PL-10）。
2. 確認簽署者名單：不同人持有、彼此使用獨立的硬體錢包、不共用電腦與密碼管理器。
3. 確認沒有任何單一 EOA 仍持有可繞過多簽的權限（例如遺留的 owner）。
4. 每半年演練一次多簽簽署流程，確認所有簽署者仍可操作。

**通過標準**：所有資金／管理權限在多簽控制下；門檻與簽署者分散性符合上述原則；演練紀錄在有效期內。

### OS-3. 金鑰備份與遺失復原程序

- [ ] **檢查項目**：每把重要金鑰都有安全的實體備份，且有書面的遺失／損毀復原程序（含人員缺席情境）。

**重要性說明**：金鑰遺失造成的損失不亞於被竊——歷史上有大量資產因「唯一持有人出事」而永久鎖死。

**執行步驟**：
1. 助記詞備份採實體介質（紙本或金屬板），存放於防火、上鎖且與工作地點分離的位置。
2. 考慮將備份拆分保管（如 Shamir 分片或分段存放兩地），避免單一地點失竊即失守。
3. 撰寫復原程序：某簽署者失聯／離職／裝置損毀時，如何輪替該簽署者；多簽本身即提供部分容錯，確認容錯數量足夠。
4. 每年驗證一次備份可用性（用備份還原到全新裝置測試）。

**通過標準**：每把金鑰有實體備份與書面復原程序；一年內驗證過備份可還原。

### OS-4. 金鑰用途分離

- [ ] **檢查項目**：不同用途使用不同金鑰：部署者、國庫／資金、日常營運、個人錢包彼此分離。

**重要性說明**：用途混用會放大單一金鑰外洩的災情，也讓權限盤點失真。部署者金鑰常因在 CI 或開發機上使用而暴露風險最高，不應同時持有資金或管理權限。

**執行步驟**：
1. 檢查部署者地址：部署完成後是否已將 owner／admin 權限移轉給多簽？部署者是否仍殘留權限或大額資金？
2. 確認團隊成員未使用個人錢包執行公務操作。
3. 高頻低額的營運操作使用獨立的低權限熱錢包，設定額度上限。

**通過標準**：每把金鑰的用途單一明確；部署者不再持有任何特權或大額資產。

### OS-5. 權限定期盤點與離職撤銷

- [ ] **檢查項目**：定期盤點所有鏈上與鏈下權限，成員離職或轉調時有標準化的權限撤銷程序。

**重要性說明**：被遺忘的權限（前員工的 GitHub 存取、舊多簽簽署者、閒置的 API key）是攻擊者最愛的入口。

**執行步驟**：
1. 每季執行權限盤點：多簽簽署者、合約角色、GitHub、雲端、網域、社群帳號、API key，逐項確認「這個人現在還應該有這個權限嗎」。
2. 建立離職檢查清單：撤多簽、移出 GitHub org、收回硬體金鑰、輪替其經手的共用機密。
3. 離職撤銷須在離職**當日**內完成，並記錄。

**通過標準**：最近一季的盤點紀錄存在；離職程序有文件且最近一次離職有完整執行紀錄。

## 人員與裝置

### OS-6. 關鍵帳號強制防釣魚 MFA

- [ ] **檢查項目**：所有關鍵服務帳號（信箱、GitHub、雲端、網域、社群平台）強制使用防釣魚的 MFA（硬體安全金鑰或 passkey），並停用簡訊驗證。

**重要性說明**：簡訊可被 SIM swap 劫持、TOTP 驗證碼可被釣魚頁面即時轉發；兩者在加密產業的攻擊中都已多次失守。硬體金鑰與 passkey 會綁定網域，釣魚頁面無法騙取。

**執行步驟**：
1. 列出關鍵服務清單，逐一檢查 MFA 設定：強制硬體金鑰／passkey、移除簡訊與電話備援選項。
2. 每人配發至少兩把硬體金鑰（一把備用，異地存放）。
3. 檢查信箱帳號的復原選項（復原電話／信箱）是否也已鎖定——攻擊者常從復原流程繞過 MFA。

**通過標準**：關鍵服務全數強制防釣魚 MFA；無簡訊備援殘留。

### OS-7. 工作裝置安全基線

- [ ] **檢查項目**：接觸程式碼或金鑰的裝置符合安全基線：全碟加密、自動更新、螢幕鎖、公私裝置分離。

**重要性說明**：裝置是所有帳號與金鑰的最終載體。一台中毒的筆電可以讓前面所有防護歸零。

**執行步驟**：
1. 制定基線：全碟加密（FileVault／BitLocker）、OS 與瀏覽器自動更新、密碼管理器、不安裝來路不明軟體、不用工作裝置進行高風險個人活動（下載破解軟體、陌生會議連結）。
2. 敏感操作（簽署多簽交易）建議使用專用裝置或至少專用瀏覽器 profile。
3. 對全員裝置做年度自查或使用 MDM 工具稽核。

**通過標準**：基線有書面文件；最近一次全員自查／稽核完成且缺失已改善。

### OS-8. 社交工程防範訓練

- [ ] **檢查項目**：全員（含非技術成員）接受過社交工程防範訓練，且知道遇到可疑接觸時的通報管道。

**重要性說明**：近年多起重大失竊源於針對性的社交工程：假冒投資人／記者的釣魚會議連結、假求職者、假錄用流程中的「測試專案」夾帶惡意程式。技術防線再強，一次成功的話術就能繞過。

**執行步驟**：
1. 每半年進行一次訓練，涵蓋當前流行的攻擊手法（假會議軟體更新、假空投、假客服）。
2. 建立「可疑接觸」通報管道，鼓勵回報，不責備誤中招的同仁（責備文化只會讓人隱匿事件）。
3. 高風險角色（財務、多簽簽署者、社群管理員）加做針對性演練（模擬釣魚）。

**通過標準**：半年內有訓練紀錄；通報管道存在且成員知悉。

## 帳號與基礎設施

### OS-9. 網域與 DNS 保護

- [ ] **檢查項目**：官方網域已啟用註冊商鎖定（registrar lock）、DNSSEC，且網域帳號受 OS-6 等級的 MFA 保護。

**重要性說明**：DNS 劫持可以把官方網址指向攻擊者的釣魚前端，使用者完全無從分辨——這類攻擊已多次造成大規模損失。

**執行步驟**：
1. 確認網域註冊商帳號的 MFA 與存取人員名單。
2. 啟用 registrar lock／transfer lock 與 DNSSEC。
3. 設定 DNS 紀錄變更的監控警示（可納入 PL-9 的監控範圍）。
4. 網域到期自動續約，綁定的付款方式有效。

**通過標準**：上述設定逐項確認完成；DNS 變更有監控。

### OS-10. 社群帳號保護

- [ ] **檢查項目**：官方社群帳號（X/Twitter、Discord、Telegram 等）有管理員盤點、最小權限與防釣魚 MFA。

**重要性說明**：官方帳號被盜後發出的釣魚連結，因為自帶官方信任，受害率極高；Discord 管理員被社交工程進而全群發釣魚，是最常見的事件類型之一。

**執行步驟**：
1. 盤點每個平台的管理員名單，移除離職者與閒置權限（對照 OS-5）。
2. 全部管理帳號啟用硬體金鑰 MFA；Discord 伺服器開啟異動保護與 bot 權限審查。
3. 制定帳號被盜的應變步驟（誰有權限申訴／凍結、如何通知社群），納入事件應變計畫。

**通過標準**：各平台管理員名單為最新；MFA 全數啟用；被盜應變步驟已寫入應變計畫。

### OS-11. GitHub 組織安全設定

- [ ] **檢查項目**：GitHub organization 已強制 2FA、主分支有保護規則、開啟機密掃描。

**重要性說明**：程式碼庫被入侵可以直接污染部署產物（惡意 commit、竄改 CI），是典型的供應鏈入口。

**執行步驟**：
1. Organization 設定強制 2FA；成員與外部協作者名單定期盤點。
2. 主分支開啟 branch protection：禁止直接 push、要求 PR review 與 CI 通過。
3. 開啟 secret scanning 與 push protection，避免金鑰誤入版本庫。
4. 檢查已安裝的 GitHub Apps 與 Actions 權限，移除不再使用者。

**通過標準**：上述設定逐項確認；成員與 App 權限盤點在一季內。

### OS-12. CI/CD 與機密資訊管理

- [ ] **檢查項目**：CI/CD 中的機密（RPC key、部署私鑰、API token）受控管理，部署流程不暴露高權限金鑰。

**重要性說明**：CI 是「拿到一點權限就能碰到所有東西」的節點；歷史上多次供應鏈攻擊都是從 CI 的機密外洩開始。

**執行步驟**：
1. 機密一律存於 CI 的 secret 管理功能或專用 vault，嚴禁寫死在程式碼或設定檔中。
2. 部署用金鑰遵循 OS-4：僅有部署所需的最小權限與資金。
3. 限制哪些 workflow／分支可以取用機密；fork 的 PR 不可觸及機密。
4. 定期輪替機密，離職時立即輪替其經手項目。

**通過標準**：repo 掃描無明文機密；機密清單有負責人與上次輪替日期。

## 供應鏈

### OS-13. 相依套件鎖定與審查

- [ ] **檢查項目**：所有相依套件（合約函式庫與前端／工具鏈）版本鎖定，更新經過審查。

**重要性說明**：惡意套件與被接管的套件版本是現成的攻擊管道；自動升級等於讓陌生人隨時能改你的程式碼。

**執行步驟**：
1. 使用 lockfile 並在 CI 驗證；合約依賴以固定版本／commit 引入（對照審計就緒清單 AR-2）。
2. 升級依賴時檢視 changelog 與 diff，特別留意維護者變更。
3. 啟用相依性漏洞警示（如 Dependabot alerts），有人負責處理。

**通過標準**：無浮動版本；依賴更新有審查紀錄；漏洞警示有人跟進。

### OS-14. 前端部署完整性

- [ ] **檢查項目**：前端建置與部署管道受控，能偵測未經授權的前端變更。

**重要性說明**：攻擊者不必碰你的合約——只要改掉前端讓使用者簽下惡意交易即可。前端劫持（透過 DNS、CDN、CI 或第三方腳本）已是主流攻擊手法。

**執行步驟**：
1. 前端部署只能經由受保護的 CI 管道（對照 OS-11、OS-12），不可有人工直傳。
2. 盡量減少第三方腳本；必要的外部資源使用 SRI（subresource integrity）。
3. 監控正式站台內容的非預期變更（定期比對建置產物雜湊）。
4. 若提供 IPFS 或鏡像版本，公告官方雜湊讓使用者可驗證。

**通過標準**：部署路徑單一且受控；有前端變更監控或雜湊比對機制。

## 事件準備

### OS-15. 緊急聯絡資源就緒

- [ ] **檢查項目**：外部緊急支援管道已預先建立並寫入事件應變計畫，包括 SEAL 911 等白帽救援資源。

**重要性說明**：事發當下才開始找人，會浪費最關鍵的黃金時間。預先建立的管道（審計方、SEAL 911、交易所聯絡窗口）能在幾分鐘內召集到專業支援。

**執行步驟**：
1. 將 [SEAL 911](https://securityalliance.org/)（Security Alliance 營運的緊急白帽救援管道，Telegram：@seal_911_bot）加入事件應變計畫的外部聯繫清單。
2. 確認過往審計方的緊急聯絡方式仍有效。
3. 預先整理主要交易所與穩定幣發行方的凍結申請管道。

**通過標準**：[事件應變計畫](incident-response-plan-template.zh-TW.md)的外部聯繫清單包含上述資源且經過驗證。
