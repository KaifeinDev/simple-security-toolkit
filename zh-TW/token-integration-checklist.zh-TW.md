# 第三方代幣整合檢查清單

> **版權與授權聲明**：本文件由本專案維護者原創撰寫，主題架構參考 Trail of Bits [Building Secure Contracts](https://secure-contracts.com/) 的 token integration checklist（AGPL-3.0）與 [d-xo/weird-erc20](https://github.com/d-xo/weird-erc20) 整理的非標準代幣行為，未直接複製其內容；具體條文請以文末參考來源的原始文件為準。

> **使用方式**：協定每次要支援一個**新的第三方代幣**（作為抵押品、交易對、獎勵資產等）之前，由整合負責人逐項完成本清單。大量歷史事件源於「假設所有 ERC20 行為一致」——實際上非標準代幣（手續費代幣、彈性供給、可重入掛勾）一再造成協定被抽乾。**任何一項未通過時，應停止上架或針對該行為實作專門處理。**

## 盡職調查

### TI-1. 代幣合約基本盡職調查

- [ ] **檢查項目**：代幣合約原始碼已在區塊鏈瀏覽器驗證、有審計紀錄，且非近期部署的不明合約。

**重要性說明**：整合一個代幣等於把它的全部行為（與全部漏洞）引入你的系統。未驗證或無審計的代幣，行為完全不可預期。

**執行步驟**：
1. 確認原始碼已驗證，且不是可疑的 proxy 指向未驗證 implementation。
2. 查詢該代幣的審計報告與歷史事件（Solodit 可搜尋歷史審計發現）。
3. 檢查部署時間、持有人數量與鏈上活動是否與其宣稱的知名度相符（防止同名假幣——**一律以合約地址為準，不以符號為準**）。

**通過標準**：原始碼已驗證、來源地址經雙人核對、無未解決的重大歷史漏洞。

### TI-2. 特權功能盤點

- [ ] **檢查項目**：已盤點代幣合約的所有特權功能：增發（mint）、暫停（pause）、黑名單（blacklist）、凍結、升級（upgradeable proxy）、參數調整（如手續費率）。

**重要性說明**：代幣方的權限就是你協定的風險：可暫停或黑名單的代幣（如 USDC、USDT）可能讓你的合約資產突然無法轉出；可升級的代幣意味著行為隨時可能改變；無上限增發則可能稀釋抵押品價值。

**執行步驟**：
1. 逐一檢查合約中的特權函式與其控制者（EOA？多簽？時間鎖？）。
2. 針對每項權限回答：「若代幣方明天行使這個權限，我的協定會發生什麼事？」並記錄結論。
3. 可升級代幣需額外評估：升級控制者是誰、是否接受「行為未來可能任意改變」的風險。

**通過標準**：特權清單與影響評估完成並存檔；不可接受的權限組合已否決上架或有專門緩解。

### TI-3. 供給分布與流動性評估

- [ ] **檢查項目**：已評估代幣的供給集中度、流動性深度，以及是否可被閃電貸／閃電鑄造大量取得。

**重要性說明**：若單一持有者掌握大部分供給、或代幣可被閃電貸大量借出，價格操縱與治理攻擊的成本會非常低——把這種代幣當抵押品或餵入價格計算，等於為攻擊者開門。

**執行步驟**：
1. 檢視前十大持有地址佔比與其性質（合約？交易所？個人？）。
2. 評估主要交易場所的流動性深度，估算把價格推動 20% 所需的資金量。
3. 確認代幣本身是否支援 flash mint，以及主要借貸市場可閃電貸出的數量。
4. 若用作抵押品或價格輸入：確認 oracle 來源能抵抗短時間操縱（避免直接使用現貨池即時價格）。

**通過標準**：集中度與操縱成本評估完成；抵押／定價用途有抗操縱的價格來源。

## 行為檢查

### TI-4. ERC20 介面符合性

- [ ] **檢查項目**：已確認代幣對 ERC20 標準的偏離之處：回傳值、`decimals`、特殊限制。

**重要性說明**：許多老牌代幣並不完全符合 ERC20：有的 `transfer` 不回傳布林值（如 USDT），有的失敗時回傳 `false` 而不 revert——用標準介面直接呼叫，可能造成交易意外失敗、或**失敗被當成成功**。

**執行步驟**：
1. 檢查 `transfer`／`transferFrom`／`approve` 的回傳行為：是否回傳 bool？失敗時 revert 還是回傳 `false`？
2. 檢查 `decimals`（不要假設是 18；USDC/USDT 為 6），確認協定的數學運算對不同 decimals 正確。
3. 檢查特殊限制：轉帳到零地址／自身地址的行為、零金額轉帳是否 revert、單筆轉帳上限。

**通過標準**：偏離清單完成；每項偏離都確認協定端已正確處理（配合 TI-7）。

### TI-5. 轉帳金額完整性

- [ ] **檢查項目**：已確認「實際到帳金額」是否恆等於「轉帳參數金額」——檢查轉帳手續費（fee-on-transfer）與彈性供給（rebasing）行為。

**重要性說明**：手續費代幣讓實收金額小於參數金額，彈性供給代幣讓餘額隨時間自行變動。以參數金額記帳的協定，內部帳目會與實際餘額脫節，最終可被套利抽乾——這是最常見的代幣整合漏洞類型之一。

**執行步驟**：
1. 檢視代幣的 `transfer` 實作是否有抽成邏輯；注意有些代幣**目前費率為 0 但保留開啟權限**（對照 TI-2）。
2. 確認是否為 rebasing 代幣（餘額會不經轉帳而變動）。
3. 任一為「是」：決定拒絕上架，或實作專門處理（以實收金額記帳、rebasing 用包裝代幣隔離）。

**通過標準**：兩種行為都已確認；有此類行為的代幣已有對應的專門處理或被否決。

### TI-6. 重入掛勾檢查

- [ ] **檢查項目**：已確認代幣轉帳是否會呼叫收款方／付款方的掛勾函式（如 ERC777 的 hooks、ERC677 的 `transferAndCall`），形成重入點。

**重要性說明**：帶掛勾的代幣讓「單純的轉帳」變成「把執行權交給外部地址」——攻擊者可在掛勾中重入你的協定。imBTC（ERC777）對 Uniswap V1 與 Lendf.Me 的重入攻擊即是經典案例。

**執行步驟**：
1. 檢查代幣是否實作 ERC777、ERC677、ERC1363 或其他會在轉帳時呼叫外部合約的機制。
2. 若有掛勾：檢視協定所有涉及該代幣轉帳的函式是否嚴格遵循 CEI／FREI-PI 模式（對照審計就緒清單 AR-13），必要時加上重入鎖。
3. 無法完整驗證時，傾向拒絕上架帶掛勾的代幣。

**通過標準**：掛勾行為已確認；有掛勾的代幣經過重入路徑分析並有防護。

## 整合實作

### TI-7. 使用安全轉帳包裝

- [ ] **檢查項目**：協定中所有 ERC20 操作皆透過安全包裝函式庫（如 OpenZeppelin `SafeERC20` 或 Solmate `SafeTransferLib`），不直接呼叫 `transfer`／`approve`。

**重要性說明**：安全包裝統一處理「不回傳值」與「回傳 false」兩類非標準行為，是抵禦 TI-4 問題的標準做法。

**執行步驟**：
1. 全域搜尋直接呼叫 `.transfer(`、`.transferFrom(`、`.approve(` 的位置，改用 `safeTransfer` 等包裝。
2. 確認未檢查回傳值的呼叫已全數消除（Slither 會標出 `unchecked-transfer`）。

**通過標準**：程式碼中無裸呼叫 ERC20 函式；Slither 相關檢查乾淨。

### TI-8. approve 相容性處理

- [ ] **檢查項目**：協定對外部合約設定授權時，已處理「非零改非零會 revert」的代幣（如 USDT）。

**重要性說明**：部分代幣要求先把 allowance 歸零才能改成新值。未處理的協定在整合這類代幣時，授權流程會在某些狀態下永久卡死。

**執行步驟**：
1. 檢視所有 `approve` 呼叫點，改用 `forceApprove`（OpenZeppelin v5）或「先歸零再設值」模式。
2. 測試同一 spender 連續兩次設定非零授權的流程。

**通過標準**：授權流程對 USDT 型代幣測試通過。

### TI-9. 以實收金額記帳

- [ ] **檢查項目**：所有代幣入金路徑皆以「轉帳前後餘額差」記帳，而非直接採用函式參數的金額。

**重要性說明**：這是對 TI-5 各種金額偏差行為的通用防禦——無論代幣抽多少費，帳目永遠與實際到帳一致，內部會計不會被撐開缺口。

**執行步驟**：
1. 檢視每個入金函式：記帳金額是否來自 `balanceAfter - balanceBefore`。
2. 注意此模式與重入的交互作用（配合 TI-6 的防護），並考慮直接向合約轉幣（donation）對餘額差計算的影響。

**通過標準**：所有入金路徑以實收金額記帳，或有書面理由說明為何不需要。

### TI-10. 針對該代幣的整合測試

- [ ] **檢查項目**：已在 mainnet fork 環境，用**真實的代幣合約**執行過協定的完整流程測試。

**重要性說明**：mock 代幣測不出真實代幣的怪異行為。用 fork 環境直接對真實合約測試，是驗證前面所有檢查結論的最終手段。

**執行步驟**：
1. 以 Foundry fork 測試對真實代幣地址執行協定的完整生命週期（存入、操作、提領）。
2. 針對 TI-4／TI-5 發現的非標準行為，各寫一個對應的測試案例。
3. 將這些測試納入回歸測試套件——代幣可升級時尤其重要（行為可能改變）。

**通過標準**：fork 測試全數通過並納入 CI 或定期執行清單。

## 治理

### TI-11. 上架決策與紀錄

- [ ] **檢查項目**：本清單的完成結果經過第二人複核，上架決策（含風險參數）有書面紀錄與簽核。

**重要性說明**：代幣上架是風險決策而非純技術操作。留下紀錄才能在日後行為改變（費率開啟、升級）時，回溯當初的評估前提並重新檢查。

**執行步驟**：
1. 將 TI-1～TI-10 的結果彙整成上架評估文件，由整合負責人以外的第二人複核。
2. 記錄核准的風險參數（抵押率、額度上限）與其依據。
3. 為該代幣設定持續監控（升級事件、特權操作、流動性驟降——可納入上線前清單 PL-9 的監控範圍）。

**通過標準**：評估文件經簽核存檔；監控項目已上線。
