> **使用方式**：本清單供開發團隊或外部廠商在送交外部審計**之前**逐項自我檢查。每個項目都有唯一編號（AR-x 為基本要求、AR-N-x 為加分項目），包含「檢查項目、重要性說明、執行步驟、通過標準」。審計昂貴且需提前數月排程——完成本清單能先清掉容易發現的問題，讓審計人員把時間花在更深層、更關鍵的漏洞上。

## 基本品質檢查清單

### AR-1. 使用最新主要版本的 Solidity

- [ ] **檢查項目**：專案使用 Solidity 的[最新](https://docs.soliditylang.org/en/latest/)主要版本。

**重要性說明**：新版本會修正已知的編譯器漏洞並內建更多保護（例如 0.8 之後的溢位檢查）。使用舊版本等於把已被修掉的問題重新帶回程式碼。

**執行步驟**：
1. 到 [Solidity 官方文件](https://docs.soliditylang.org/en/latest/)確認目前最新的主要版本。
2. 檢查所有合約檔案的 `pragma solidity` 宣告與建置設定（`foundry.toml` 的 `solc_version` 或 `hardhat.config` 的 `solidity.version`）。
3. 若版本落後，升級並重新執行完整測試。
4. 檢查所用版本是否有已公告的 [已知 bug 清單](https://docs.soliditylang.org/en/latest/bugs.html)影響到你的程式碼。

**通過標準**：所有合約使用同一個、且為目前最新主要版本的編譯器；升級後全部測試通過。

### AR-2. 優先使用成熟的函式庫

- [ ] **檢查項目**：能用成熟函式庫解決的功能（ERC 標準、權限控制、數學運算、安全轉帳等），不自行重新實作。

**重要性說明**：[OpenZeppelin contracts](https://github.com/OpenZeppelin/openzeppelin-contracts/) 將安全性置於一切之上，且大多數審計人員已相當熟悉，能大幅減少審計時間；[Solmate contracts](https://github.com/Rari-Capital/solmate) 則是在 gas 優化至關重要時的不錯替代方案。自行實作標準功能是漏洞的常見來源。

**執行步驟**：
1. 盤點程式碼中所有「自行實作、但已有標準函式庫版本」的元件（ERC20/721、Ownable、ReentrancyGuard、SafeERC20 等）。
2. 除非有書面記錄的明確理由（gas、功能差異），一律改用 OpenZeppelin（或 Solmate）。
3. 確認函式庫是透過套件管理（npm／forge install 固定版本）引入，而不是複製貼上後自行修改；若必須修改，将 diff 明確標註並告知審計方。

**通過標準**：所有標準功能皆來自成熟函式庫的固定版本；任何自行實作或修改處都有書面理由。

### AR-3. 正常路徑與 revert 測試全數通過

- [ ] **檢查項目**：針對「正常路徑（happy path）」的使用情境撰寫測試，並針對預期應該失敗的操作撰寫預期會 revert 的測試；所有測試皆通過。

**重要性說明**：審計人員的時間不該花在「這功能到底能不能動」上。revert 測試同樣重要——存取控制與輸入驗證的漏洞，往往就是「該失敗的操作沒有失敗」。

**執行步驟**：
1. 為每個對外函式列出：正常使用情境（至少一個測試）＋每一個 `require`／`revert` 條件（各至少一個觸發測試，Foundry 可用 `vm.expectRevert`）。
2. 檢查每個測試都有實質的斷言（檢查狀態變化與事件），而不是只呼叫函式沒有驗證結果。
3. 在乾淨環境執行 `forge test`（或對應指令），確認全數通過、無被跳過（skip）的測試。

**通過標準**：每個對外函式都有正常路徑與 revert 測試；CI 上全部測試通過。

### AR-4. 導入模糊測試

- [ ] **檢查項目**：專案已導入模糊測試（fuzz testing），且核心不變量有對應的 invariant 測試。

**重要性說明**：模糊測試已被證實在挖掘漏洞上相當有效——它會嘗試你想不到的輸入組合，特別擅長找出邊界條件與算術問題。

**執行步驟**：
1. 選擇工具：[Foundry](https://github.com/foundry-rs/foundry) 與 [Echidna](https://github.com/crytic/echidna) 都支援無狀態與有狀態的模糊測試；若使用 [Hardhat](https://github.com/NomicFoundation/hardhat)，也值得額外導入上述工具。
2. 對接受數值輸入的函式撰寫 fuzz 測試：讓工具產生隨機輸入，並斷言輸出性質（如單調性、上下界）。
3. 定義系統層級不變量（例如「合約代幣餘額 ≥ 所有使用者存款總和」），依 [Foundry Invariants 參考指南](https://book.getfoundry.sh/forge/invariant-testing?highlight=invariant#invariant-testing)設定 invariant 測試。
4. 提高執行次數（例如 runs ≥ 10,000）跑一輪完整測試。

**通過標準**：核心數學／狀態轉換函式皆有 fuzz 測試；至少 3–5 條系統不變量有 invariant 測試且長時間執行不被打破。

### AR-5. 執行靜態分析並處理結果

- [ ] **檢查項目**：已對程式碼執行靜態分析工具（首選 [Slither](https://github.com/crytic/slither)，[MythX](https://mythx.io/) 為替代方案），並逐項處理其結果。

**重要性說明**：這些工具經常對非問題發出警告，但也能便宜且快速地抓到容易發現的基本問題（重入、未檢查回傳值等）。審計人員一定會跑 Slither——與其讓他們把時間花在這些基本問題上，不如自己先清掉。

**執行步驟**：
1. 安裝並執行：`slither .`。
2. 逐項分類每個發現：真問題（修正）／誤報（在追蹤文件或 triage 設定中記錄理由）。
3. 修正後重新執行，確認高／中嚴重度項目已全數處理。
4. 建議將 Slither 加入 CI（見開發流程文件），避免新程式碼再引入相同問題。

**通過標準**：Slither 輸出中的每一項都有處置紀錄（已修正或附理由的誤報），無未處理的高／中嚴重度項目。

### AR-6. 部署／升級腳本納入審計範圍

- [ ] **檢查項目**：部署腳本與模擬升級腳本（若適用）已準備完成，並列入審計範圍。

**重要性說明**：部署與升級的重要性不亞於執行期程式碼。錯誤的初始化參數、順序或權限設定，即使合約本身無 bug 也能造成災難（未初始化的 proxy 是經典案例）。

**執行步驟**：
1. 撰寫可重複執行的部署腳本（不要手動逐筆部署），包含所有初始化參數與權限移轉。
2. 若採可升級架構，準備一份模擬升級腳本並在 fork 環境演練。
3. 在審計範圍文件中明確列入這些腳本。

**通過標準**：部署／升級腳本存在於 repo、可在 fork 環境成功執行，且審計合約範圍清單中包含它們。

### AR-7. 所有函式皆有文件（NatSpec）

- [ ] **檢查項目**：所有函式皆有文件；`public`／`external` 函式使用 [NatSpec 文件](https://docs.soliditylang.org/en/develop/natspec-format.html)（視為合約公開介面的一部分）。

**重要性說明**：審計本質上是在比對「程式碼實際做的事」與「你想要它做的事」。沒有文件，審計人員只能猜測意圖，浪費時間又可能漏掉「實作與意圖不符」這類最關鍵的 bug。

**執行步驟**：
1. 為每個 `public`／`external` 函式補齊 NatSpec：`@notice`（做什麼）、`@param`、`@return`，必要時加 `@dev`（注意事項、前置條件）。
2. `internal`／`private` 函式至少有一行註解說明用途。
3. 用 `forge doc` 或編譯器輸出檢查 NatSpec 是否完整解析。

**通過標準**：抽查任一對外函式都能只靠文件理解其行為與限制；文件描述與實作一致。

### AR-8. 編譯無錯誤與警告

- [ ] **檢查項目**：合約編譯時沒有任何編譯器錯誤或**警告**。

**重要性說明**：警告常常指向真實問題（shadowing、未使用變數、隱式轉型）。滿是警告的建置輸出也會把真正重要的訊息淹沒。

**執行步驟**：
1. 執行乾淨建置（`forge clean && forge build`），記錄所有警告。
2. 逐一修正；確實無法避免者，記錄理由。

**通過標準**：乾淨建置輸出零錯誤、零警告（或每個殘留警告都有書面理由）。

### AR-9. 完成拼字檢查

- [ ] **檢查項目**：對程式碼（含註解與文件）執行過拼字檢查。

**重要性說明**：這關乎專業印象——滿是錯字的程式碼會讓審計人員（與潛在使用者）懷疑團隊的細心程度。錯字偶爾也會出現在識別字上造成實際混淆。

**執行步驟**：
1. 使用工具掃描，例如 [codespell](https://github.com/codespell-project/codespell) 或 [cspell](https://cspell.org/)（可加入 CI）。
2. 修正錯字；專案術語加入字典檔避免誤報。

**通過標準**：拼字檢查工具在合約與文件上執行結果乾淨。

### AR-10. 盡量避免使用 assembly

- [ ] **檢查項目**：程式碼中僅在有明確必要時才使用組合語言（assembly），且每一處都有完整說明。

**重要性說明**：assembly 捨棄了 Solidity 的防護機制（型別、溢位、邊界檢查），必須被更謹慎地檢查，會顯著拉長審計時間與費用，也更容易藏漏洞。

**執行步驟**：
1. 搜尋所有 `assembly` 區塊（`grep -rn "assembly" src/`）。
2. 對每一處問：能否用純 Solidity 改寫？gas 差異是否真的值得？不值得就改寫。
3. 保留的 assembly：**每一行**都要有註解，並附整體安全性說明（參照開發流程文件的要求）。

**通過標準**：每個殘留的 assembly 區塊都有「為何必要」的書面理由與逐行註解。

### AR-11. 記錄所有 `unchecked` 的安全理由

- [ ] **檢查項目**：所有 `unchecked` 區塊都附有文件，具體說明*為何*可以安全地省略算術檢查，最好針對每個運算分別說明。

**重要性說明**：`unchecked` 等於自行擔保「這裡不會溢位」。沒有寫下推理過程，審計人員必須自己重建證明，而你自己也可能在日後修改時破壞原本成立的前提。

**執行步驟**：
1. 搜尋所有 `unchecked` 區塊（`grep -rn "unchecked" src/`）。
2. 為每個區塊撰寫 `// Safety:` 註解，逐運算說明不會溢位／下溢的理由（範例見[開發流程文件](development-process.zh-TW.md)）。
3. 無法清楚證明安全的，移除 `unchecked`。

**通過標準**：每個 `unchecked` 區塊上方都有逐運算的 Safety 註解，且推理經第二人檢查。

### AR-12. `public` 函式盡可能改為 `external`

- [ ] **檢查項目**：任何可以改為 `external` 的 `public` 函式，都已改為 `external`。

**重要性說明**：這不僅是 gas 上的考量，更能降低審計人員的認知負擔——`external` 減少了該函式可能被呼叫的情境數量（排除內部呼叫），要分析的路徑更少。

**執行步驟**：
1. 列出所有 `public` 函式（Slither 的 `external-function` detector 會直接標出可改的項目）。
2. 對每個函式確認合約內部是否有呼叫；沒有就改為 `external`。
3. 重新編譯並執行測試。

**通過標準**：Slither `external-function` 檢查無剩餘項目；保留為 `public` 的函式皆確實有內部呼叫需求。

### AR-13. 採用 FREI-PI 模式驗證協定不變量

- [ ] **檢查項目**：盡可能在各處使用[函式需求-效果-互動-協定不變量（FREI-PI）模式](https://www.nascent.xyz/idea/youre-writing-require-statements-wrong)；所有代幣與 ETH 轉帳都視為「互動（interactions）」，並在每次互動結束時驗證系統層級的協定不變量仍然成立。

**重要性說明**：傳統的 CEI（檢查-效果-互動）只保護單一函式；FREI-PI 進一步要求在函式結尾驗證**整個協定**的核心不變量，即使函式內部邏輯有 bug，只要不變量檢查在，就能擋下許多災難性結果。

**執行步驟**：
1. 明文寫下協定的核心不變量（例如「儲備金恆等式」「總股份對應總資產」）。
2. 檢視每個使用者進入點函式，確認順序符合：Requirements（檢查）→ Effects（狀態更新）→ Interactions（外部呼叫/轉帳）→ Protocol Invariants（結尾驗證不變量）。
3. 把不變量實作成可重用的檢查函式，在各進入點結尾呼叫。
4. 與 AR-4 的 invariant fuzz 測試相互對照，確保寫下的不變量都有被測試。

**通過標準**：核心不變量有書面清單；每個使用者進入點在結尾驗證不變量（或有記錄不需驗證的理由）。

### AR-14. 請外部可信開發者做合理性檢查

- [ ] **檢查項目**：至少一位組織之外、值得信任的 Solidity 開發者或資安人員，已對合約完成合理性檢查（sanity check）。

**重要性說明**：如果你的程式碼問題重重、需要大幅修改，你會希望盡早（且免費地）從可信賴的朋友那裡得知，而不是在昂貴的審計之後才發現——審計方不會幫你重構，只會把問題列出來收費。

**執行步驟**：
1. 找 1–2 位外部可信的 Solidity 開發者／資安人員（簽 NDA 若有需要）。
2. 提供架構說明與程式碼，請對方花數小時給出整體回饋：架構是否合理、複雜度是否失控、有沒有明顯的問題徵兆。
3. 記錄回饋並處理重大問題後，再送正式審計。

**通過標準**：有至少一份外部檢查的回饋紀錄，且重大疑慮已在送審前處理。

## 加分項目

### AR-N1. 形式化驗證

- [ ] **檢查項目**：使用形式化驗證（formal verification）工具驗證核心不變量。

**說明與步驟**：挑選最關鍵的 1–3 條不變量（通常是資產守恆類），使用 [Certora](https://www.certora.com/) 或 [Runtime Verification](https://runtimeverification.com/) 等常用（付費）工具撰寫規格並驗證。注意：實務上目前的形式化驗證工具並非萬靈丹，仍有未涵蓋的邊緣案例——把它當成 fuzz 測試之上的另一層保險，而不是替代品。

**通過標準**：核心不變量有形式化規格且驗證通過；工具的假設與限制有記錄。

### AR-N2. 寫下額外的資安假設

- [ ] **檢查項目**：以書面記錄協定的額外資安假設。

**說明與步驟**：不需要非常正式，例如：「我們假設 `owner` 不是惡意的、Chainlink oracle 不會謊報代幣價格、Chainlink oracle 至少每 24 小時會回報一次價格、`owner` 核准的所有代幣都是符合 ERC20 標準且沒有轉帳掛勾（transfer hooks）的代幣，並且鏈上永遠不會發生超過 30 個區塊的重組（reorg）。」這能幫助你理解*即使合約沒有 bug*，事情仍可能出錯的方式。優秀的審計人員能幫你判斷這些假設是否合理，也可能指出你沒意識到自己正在做的假設。

**通過標準**：假設清單已寫成文件並提供給審計方。

### AR-N3. 列出希望審計方特別關注的區域

- [ ] **檢查項目**：已列出自己沒把握、或希望審計人員多花時間的程式碼區域。

**說明與步驟**：請每位開發者提名「最沒把握的地方」（複雜的數學、精度處理、外部整合、時間相關邏輯等），彙整成清單與審計方分享。這不會讓你顯得不專業——反而能讓審計時間花在刀口上。

**通過標準**：清單已交付審計方。

### AR-N4. 填寫審計範圍界定表
