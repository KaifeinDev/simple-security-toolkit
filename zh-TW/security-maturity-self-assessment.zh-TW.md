# 組織安全成熟度自評清單（改編自 The Rekt Test）

> **版權與授權聲明**：本文件改編自 [The Rekt Test](https://blog.trailofbits.com/2023/08/14/can-you-pass-the-rekt-test/)——由 Trail of Bits、Immunefi 等多家資安機構組成的工作小組於 2023 年共同發布的 12 題 Web3 安全自評問題。原始問題之著作權歸原作者所有；本文件的中文改寫、補充說明與檢查步驟由本專案維護者提供，僅供內部與合作廠商評估使用，非官方翻譯。

> **使用方式**：本清單是 12 題**是非題**，供主管層或專案負責人快速評估組織整體的安全成熟度，一次會議（約 1 小時）即可完成。每題只有「是／否」兩種答案——**只有在能出示對應證據時才能答「是」**。答「否」的題目即為改善事項，建議排入待辦並指定負責人與期限。答「是」的題數越少，代表被駭時損失慘重的風險越高；若過半數答「否」，應視為重大警訊，優先補強後再考慮擴大管理的資產規模。

## 第一部分：系統文件化

### SM-1. 所有角色與權限皆已文件化？

- [ ] **檢查項目**：系統中所有的參與者（actors）、角色（roles）與特權（privileges）都有書面文件。

**重要性說明**：不知道「誰能做什麼」就無法評估風險。多數重大事件的根因之一，是某個被遺忘的特權角色（舊的 admin key、測試帳號）被攻擊者利用。

**檢查方式**：
1. 要求出示角色權限文件，內容應涵蓋：鏈上角色（owner、admin、pauser、upgrader、多簽簽署者）與鏈下角色（基礎設施管理員、社群帳號管理員）。
2. 抽查一兩個合約的實際鏈上權限（`owner()` 等），與文件比對是否一致。

**通過標準**：文件存在、涵蓋鏈上與鏈下、抽查一致，且有指定的維護負責人。

### SM-2. 所有依賴的外部服務、合約與 oracle 皆已文件化？

- [ ] **檢查項目**：所有依賴的外部服務、第三方合約與 oracle 都有清單記錄。

**重要性說明**：你的安全上限取決於依賴項的安全。Oracle 異常、依賴協定被駭、RPC 服務中斷，都可能直接衝擊你的系統——沒有清單，就不知道自己暴露在哪些風險之下。

**檢查方式**：
1. 要求出示依賴清單：鏈上（oracle、AMM、借貸協定、跨鏈橋、代幣合約）與鏈下（RPC 供應商、託管服務、CI、雲端）。
2. 每個依賴項應標注：故障或被駭時對本系統的影響、以及對應的應變方式。

**通過標準**：清單完整且每項依賴都有影響評估；與[審計就緒清單](audit-readiness-checklist.zh-TW.md)的 AR-N2（資安假設）相互對應。

### SM-3. 有書面且演練過的事件應變計畫？

- [ ] **檢查項目**：有書面的事件應變計畫，**且**實際演練過。

**重要性說明**：沒有計畫，事發當下每分鐘都在燒錢；沒演練過的計畫，事發當下多半跑不動。

**檢查方式**：
1. 要求出示計畫文件——可直接檢查是否依[事件應變計畫範本](incident-response-plan-template.zh-TW.md)填寫完整（無空白欄位）。
2. 查驗最近一次演練（tabletop exercise）的日期與檢討紀錄。

**通過標準**：計畫完整、6 個月內演練過至少一次、演練發現的問題已回饋更新到計畫中。

### SM-4. 有文件記錄攻擊自己系統的最佳方式？

- [ ] **檢查項目**：團隊有以攻擊者視角撰寫的文件，記錄攻擊自己系統的最可行途徑（威脅模型）。

**重要性說明**：如果你自己都說不出「駭客會怎麼打我」，就不可能有針對性的防禦。這份文件也是審計方與新進資安人員最快進入狀況的材料。

**檢查方式**：
1. 要求出示威脅模型文件：最有價值的攻擊標的（資金池、admin key、oracle）、可行的攻擊路徑、對應的緩解措施。
2. 確認文件在重大功能上線後有更新。

**通過標準**：文件存在且涵蓋主要資產與攻擊面；與[審計就緒清單](audit-readiness-checklist.zh-TW.md) AR-N3（提供審計方的關注清單）相互支援。

## 第二部分：人員安全

### SM-5. 對所有員工進行身分驗證與背景調查？

- [ ] **檢查項目**：所有員工（含遠端與匿名文化濃厚的環境）在到職前經過身分驗證與背景調查。

**重要性說明**：Web3 產業已多次發生攻擊者（含國家級行為者）以假身分應徵入職、進而竊取金鑰或植入後門的案例。內部人是最短的攻擊路徑。

**檢查方式**：
1. 查驗招聘流程是否包含：身分文件驗證、視訊面試、推薦人查核；敏感職位（能接觸金鑰、正式環境）加做背景調查。
2. 抽查最近入職成員的查核紀錄。

**通過標準**：流程有文件、有執行紀錄，敏感職位無例外。

### SM-6. 有職責中明確包含資安的團隊成員？

- [ ] **檢查項目**：至少有一位團隊成員的職務說明中明確包含資安職責。

**重要性說明**：「大家都負責」等於沒有人負責。資安需要有人持續盯著：追蹤新漏洞情報、管理懸賞回報、推動演練與稽核。

**檢查方式**：確認該成員的職務內容、實際投入時間，以及是否有向管理層直接匯報安全狀態的管道。

**通過標準**：有具名的資安負責人，且其資安職責寫入職務說明。

## 第三部分：金鑰與基礎設施

### SM-7. 正式環境系統要求使用硬體安全金鑰？

- [ ] **檢查項目**：存取正式環境系統（部署、雲端主控台、GitHub、網域、社群帳號）一律要求硬體安全金鑰（如 YubiKey）作為第二因素。

**重要性說明**：簡訊與 TOTP 驗證碼都可被釣魚；SIM swap 攻擊在加密產業尤其猖獗。硬體金鑰是目前唯一能有效抵抗釣魚的 MFA。

**檢查方式**：抽查關鍵服務（GitHub org、雲端帳號、網域註冊商）的 MFA 設定，確認已強制硬體金鑰並停用簡訊備援。

**通過標準**：所有正式環境相關帳號強制硬體金鑰，無簡訊 MFA 例外。

### SM-8. 金鑰管理需要多人參與及實體步驟？

- [ ] **檢查項目**：動用關鍵金鑰（資金、升級、admin）必須經過多人同意與實體步驟（硬體錢包按鍵確認等），任何單一人員無法獨自完成。

**重要性說明**：單人掌握的金鑰，等於整個協定的安全繫於一個人的裝置與操守。多人＋實體步驟能同時防外部入侵與內部作惡。

**檢查方式**：
1. 確認關鍵操作採用多簽或 MPC，門檻合理（例如 3/5），簽署者分散在不同人與不同裝置。
2. 確認簽署使用硬體錢包，私鑰不曾以明文存在於連網電腦。

**通過標準**：無任何單人可動用的關鍵金鑰；細部檢查可用[營運安全與金鑰管理檢查清單](operational-security-checklist.zh-TW.md)。

## 第四部分：測試與工具

### SM-9. 已定義系統關鍵不變量並在每次 commit 時測試？

- [ ] **檢查項目**：系統的關鍵不變量（invariants）有明文定義，且每次 commit 都會自動執行對應測試。

**重要性說明**：不變量（如「總資產恆大於等於總負債」）是協定安全的底線。寫下來並自動化測試，才能確保任何改動都不會不小心打破它。

**檢查方式**：查驗不變量清單文件、對應的 invariant／fuzz 測試，以及 CI 設定是否每次 commit 都執行。

**通過標準**：對應[審計就緒清單](audit-readiness-checklist.zh-TW.md) AR-4 與 AR-13 皆通過，且測試掛在 CI 上。

### SM-10. 使用最好的自動化工具找出程式碼中的安全問題？

- [ ] **檢查項目**：開發流程中固定使用業界主流的自動化安全工具（靜態分析、fuzzing）。

**重要性說明**：自動化工具便宜且不知疲倦，能把人力留給只有人能發現的深層問題。不用工具等於放棄免費的防線。

**檢查方式**：確認 Slither（靜態分析）與 Foundry／Echidna（fuzzing）等工具已導入且在 CI 中執行（參照[開發流程](development-process.zh-TW.md)步驟 6、7、12）。

**通過標準**：工具在 CI 中自動執行，輸出有人負責處理。

## 第五部分：外部驗證與使用者保護

### SM-11. 有外部審計並持續經營漏洞揭露／懸賞計畫？

- [ ] **檢查項目**：程式碼經過外部審計，且有持續運作的漏洞揭露管道或懸賞計畫。

**重要性說明**：審計是上線前的體檢，懸賞是上線後的持續防線——兩者缺一不可。

**檢查方式**：查驗審計報告（含最終版與回應紀錄）、懸賞計畫頁面與最近的回報處理紀錄（參照[上線前清單](pre-launch-security-checklist.zh-TW.md) PL-5、PL-8）。

**通過標準**：至少一次外部審計完成且發現已處理；懸賞計畫上線且有人在管理。

### SM-12. 已考量並緩解系統被用來傷害使用者的途徑？

- [ ] **檢查項目**：團隊已系統性思考「本系統會被如何濫用來傷害使用者」，並對可行的濫用途徑做出緩解。

**重要性說明**：安全不只保護協定資金，也包含使用者：釣魚仿冒網站、惡意治理提案、搶跑（front-running）、詐騙代幣上架等，都會讓使用者受害、信任崩潰。

**檢查方式**：
1. 要求出示濫用情境分析：仿冒網站與假客服、MEV／搶跑對使用者的影響、治理攻擊、惡意資產上架等。
2. 確認對應緩解措施：官方管道公告與防偽提示、交易保護建議、治理時間鎖等。

**通過標準**：至少完成一次濫用情境盤點，主要情境有具體緩解措施。
